# Korean Threads — TECH

Продуктовое поведение: [PRODUCT.md](PRODUCT.md) (ссылки вида «П-N» — номер пункта Behavior). Пошаговый план реализации с кодом тестов: `docs/superpowers/plans/2026-11-14-korean-threads.md` (ссылки вида «Task N»). Этот документ задаёт решения и проверки; план остаётся рабочим списком задач и не дублируется здесь.

## Контекст

Нужно приложение для одного владельца, готовое к экзамену в феврале 2027 (около трёх месяцев). Оно размещено в интернете, чтобы открываться с телефона где угодно при выключенном Mac. Из этого следуют главные технические ограничения:

- serverless-хостинг (Vercel) и облачная БД (Supabase Postgres); состояние в памяти процесса не живёт, все гарантии (дедупликация, блокировки, лимиты) опираются на БД;
- ролей две: владелец (пароль) и зритель (аноним, только чтение, без записи состояния и без вызовов ИИ);
- банк постов генерируется заранее на Mac скриптами (лента мгновенная, расходы предсказуемы);
- разметку текста делает детерминированный морфологический анализатор, а не ИИ (проверка по спискам не зависит от того, что «придумал» ИИ);
- в облако уходят только текстовые фрагменты книг с векторами для поиска (чат); файлы книг, экзаменов и OCR-кэш остаются на Mac.

Деплой выполнен по решениям grill-сессии 2026-11-14: Vercel Hobby (регион `icn1`), Supabase Free (Seoul), анализатор в контейнере (Fly.io), код приложения в отдельной папке `korean-threads-app/` (приватный репозиторий). Netlify не используется.

## Архитектура

```
Браузер телефона (PWA)               Mac владельца (скрипты, бэкапы)
   │ HTTPS                              │ ingest-*, generate-*, pg_dump
   ▼                                    │ (dev по умолчанию, prod с --prod)
Vercel (Next.js, Fluid, icn1) ─────────►│
   │        │                           ▼
   │        └─► OpenRouter (HTTPS)   Supabase Postgres (Seoul, pgvector, pg_trgm)
   │                                     ▲
   ├─ пулер Supavisor :6543, роль приложения
   ▼
Анализатор mecab-ko-fastapi (контейнер, Fly.io, секрет в заголовке)
```

- **Next.js** отдаёт UI и тонкие `route.ts`, которые парсят запрос (Zod), определяют роль и вызывают `handle*` из `src/lib/api.ts`. Вся логика живёт в `src/lib/*` и тестируется без сервера; все `handle*` и доступ к БД — `async`.
- **Postgres (Supabase)** хранит всё: списки, состояние памяти, события, треды, проверки, чанки базы знаний. Таблицы закрыты RLS без политик; приложение ходит только с сервера (роль с минимальными правами, пулер, transaction mode, без prepared statements). `supabase-js`, anon-ключ и `service_role` в коде не используются.
- **Анализатор** нужен только при создании материала (банк, чат). Ленте он не нужен (П-64). Работает как отдельный контейнер; Vercel вызывает его с общим секретом.
- **OpenRouter** — единственный внешний сервис ИИ: письмо (`write`), лёгкие задачи (`light`), распознавание страниц (`vision`), независимое решение вопросов (`verify`), эмбеддинги (`embed`). Модели задаются переменными окружения (Task 4, Task 10). Прод-ключ отдельный, с месячным лимитом на стороне OpenRouter.
- Внешние сервисы, кроме OpenRouter, Supabase, Vercel, контейнера анализатора и 한국어기초사전 при загрузке словаря, не используются.

## Модель данных

Схема — Task 1 (13 таблиц) в версии для Postgres (Task 17) плюс служебные `rate_limits`, `chat_lock`, `login_attempts`. Решения, которые определяют поведение:

- **Идентификаторы слов и конструкций**: `v:<номер>` и `g:<номер>` по общему списку (`items`). Списки 1–6급загружаются целиком (10 635 слов, 336 конструкций), но память (`item_state`) заводится только для 1–4급 (П-8, П-47).
- **Состояние памяти** (`item_state`): `stability_days`, `last_event_at`, `is_new`, `tap_count`, `introduced_day`. Остальное (`retrievability`, приоритет, «выучено») вычисляется, не хранится.
- **События** (`events`): журнал `tap`, `viewed`, `check_right`, `check_wrong` с `post_id`/`check_id`. Состояние можно пересчитать из журнала; журнал служит и источником для дедупликации касаний и для «подтверждено за 30 дней» (П-46).
- **Посты** (`posts.body_json`): абзацы хранятся уже размеченными — сегменты `{text, itemIds, unlisted[]}`. Поэтому открытие и касание поста не зависят от анализатора (П-64) и от того, как ИИ называл начальную форму.
- **Связи** `post_items` и `check_items` — единственный вход в ранжирование ленты и в выбор проверок.
- **Проверки** (`checks`): `source ∈ {exam, topik-style, post}`; `label` для подписи (П-29). Настоящие и сгенерированные не смешиваются (П-31).
- **База знаний**: `kb_docs`, `kb_chunks` (текст, страница, `vec vector(N)` из `pgvector`; поиск по ключевым словам — GIN-индекс `pg_trgm` по `text`). В облако идут только чанки и векторы. OCR-кэш (`data/ocr/` по sha1 документа) и сами файлы лежат только на Mac.
- **Типы и перенос из SQLite**: `AUTOINCREMENT` → `bigserial`/`identity`, `BLOB` → `vector`, `FTS5` → `pg_trgm`, время — `timestamptz`/`bigint` (мс) как в `events.at`. Все таблицы создаются с `ENABLE ROW LEVEL SECURITY`, политик нет.
- **Служебные таблицы**: `rate_limits(key, window_start, count)` для лимитов на serverless и `chat_lock(owner, until)` (или `pg_advisory_lock`) для П-45; `login_attempts(ip_hash, window_start, count)` для П-54.

Нормализация: весь корейский текст приводится к NFC при записи и перед сравнением; леммы анализатора приводятся к совместимым джамо (`ᄇ`→`ㅂ`) (П-62).

## Основные потоки

### 1. Подготовка данных (оффлайн-скрипты на Mac, `scripts/*.ts`)

Скрипты пишут напрямую в Postgres (по умолчанию `dev`-проект; `prod` только с явным `--prod`). Пути к `books/` и OCR-кэшу берутся из `KB_SOURCE_DIR` (вне репозитория). Данные для prod переносятся после проверки на dev.

Порядок и зависимости (Task 2 → 6 → 7 → 8 → 10 → 11 → 12):

1. `ingest-lists` — списки 1–6급, стартовое состояние памяти (1–2급: stability 60, 3급: 4, 4급: новое; 5–6급 без строк) (П-2, П-3).
2. `ingest-kb` — книги и экзамены в базу знаний; страницы без текстового слоя (<80 символов) идут на OCR через визуальную модель с кэшем. Полный OCR стартует только с `--yes` после оценки стоимости.
3. `ingest-glosses` — русские значения из 한국어기초사전, возобновляемо; пробелы закрывает ИИ (`source='ai'`, П-20).
4. `ingest-grammar-notes` — русские пояснения 224 конструкций 1–4급 с опорой на базу знаний; выборка из 20 уходит владельцу на проверку.
5. `bake-off` → выбор `MODEL_WRITE` владельцем → `generate-bank` порциями (лента работает на том, что уже есть) (П-16).
6. `ingest-exams`, `generate-topik-style` — проверки (П-29–П-31).

Каждый скрипт возобновляем и поддерживает `--limit`/`--dry-run`, где есть расход денег.

### 2. Создание поста (общий конвейер банка и чата)

`RawThread` (JSON от ИИ) → `buildPost` (анализатор размечает корейские абзацы по морфемам; русские не трогаются) → `validatePost` → `saveThread`. Невалидный результат повторяется до 2 раз с текстом ошибок; после этого генерация возвращает `ok:false` и ничего не сохраняет.

Правила валидации банка (П-8, П-9): доля `unlisted` среди содержательных морфем ≤ 10%; нет items выше 4급, кроме одной «подтяжки» (лемма = `stretchLemma`); все целевые слова и конструкции присутствуют. Для чата (П-41) уровневые правила отключены, остаются «абзацы не пусты» и корректная разметка.

Разметка: `posGroup` относит `NNP SL SH SN SY SF SE SSO SSC SC XR UNKNOWN` к `skip` (П-10); эмодзи и `ㅠㅠ` дают сегмент без морфем, выравнивание остальных не ломается.

Грамматика ищется как подпоследовательность лемм (`grammarMatches`: раскрытие `(으)`, `아/어`, `ㅂ/습`).

### 3. Выбор карточек (`pickFeed`, Task 13) и режим зрителя

**Зритель** (`role='viewer'`): `pickViewerFeed` берёт случайные ветки с `origin='bank'`, без чат-веток, без лимита новых и без `recordDelivered`; курсор хранится на клиенте (список уже показанных id), ответ можно кэшировать на CDN (`s-maxage`) для случайного пула. Проверки зрителю — только `source IN ('topik-style','post')`, условие в SQL (П-72). Запись `events`, `item_state` и `last_delivered_at` для зрителя не выполняется ни на каком пути.

Далее — выбор для владельца:

- Оценка треда = сумма `priority = (1 − R) × LEVEL_WEIGHT[level]` по его 1–4급items (веса: 1급 0.2, 2급 0.3, 3–4급 1, 5–6급 0).
- Кандидаты: топ-3n по оценке среди тредов, не показанных за 7 дней; взвешенная случайная выборка n (П-12, П-13).
- Лимит новых слов за локальный день — 6 (по `introduced_day` и `APP_TZ`) (П-14).
- С вероятностью 12% слот занимает тред с `stretch_item_id` (П-8).
- Через каждые 12 карточек вставляется проверка (`pickCheck`): наибольший приоритет целей, не отвеченная 3 дня, `exam`/`topik-style` предпочтительнее `post` (П-28, П-32, П-36).
- Тонкий банк: если подходящих меньше n, берутся показанные раньше всех, затем возвращается сколько есть (П-15, П-16). Пустой ответ не допускается, пока в банке есть хотя бы один тред.
- `recordDelivered` проставляет `last_delivered_at` и `introduced_day` при выдаче.

### 4. События и память (Task 3, Task 14)

| Событие | Правило | П |
|---|---|---|
| `tap` | `stability = max(0.5, stability × 0.5)`, `isNew=false`; тот же `itemId` в окне 5000 мс — дедуп | 21, 22, 50 |
| `viewed` (1,5 с видимости карточки) | `×1.15` только для `!isNew` | 26, 27 |
| `check_right` | `min(180, max(1, s) × 2)`, `isNew=false` | 34, 51 |
| `check_wrong` | `max(0.5, s × 0.4)` | 34, 51 |

`retrievability = exp(−Δt / stability)`, для новых слов 0. «Выучено» = stability ≥ 7 дней и R ≥ 0.8; «подтверждено» = есть `check_right` за 30 дней (П-46). Константы собраны в `MEMORY` и `FEED`, чтобы подстраиваться по ощущениям без переписывания логики.

`check_wrong` и `check_right` применяются только к items, найденным **в различающихся частях вариантов** (`buildCheck`: объединение по вариантам минус пересечение), а не к стему (П-34).

### 5. Чат (Task 10, Task 14)

`handleChat` (только `role='owner'`; зритель → 403): валидация (пусто/длиннее 1000 → 400 без вызова ИИ, П-43) → захват блокировки чата в БД (занята → 409 «подожди ответа», П-45) → лимит чата (N в минуту, M в сутки по `rate_limits`) → `searchKb` (до 6 фрагментов, без `exam`) → `generateChatThread` → `saveThread` с `origin='chat'` и `sources` → освобождение блокировки (в `finally`, плюс `until` как предохранитель) → ответ. Любой сбой (сеть, OpenRouter, невалидный JSON, `AnalyzerError`) → 502 с русским текстом, ничего не сохраняется (П-44). Функция `/api/chat` имеет `maxDuration` (сверено с документацией: на Hobby до 300 с).

Поиск по базе знаний — гибрид: `pg_trgm` (`similarity`/`%` для запроса от 3 символов, `ILIKE` для короче) + косинус по `pgvector` (`<=>`), слияние `rrf` (k=60). Объём базы мал, достаточно точного перебора или `hnsw` без настройки.

### 6. Значение слова (`handleItem`, `handleLemma`, `GlossSheet`)

- Для слов и конструкций из списков — `item_notes` (источник `krdict` или `ai`).
- Для слов вне списков — `lemma_cache`, при промахе — словарь, затем ИИ (`source='ai'`) (П-9, П-20). Для **зрителя** ветка ИИ отключена: при промахе возвращается `{ glossRu: null }` (П-65, П-73). Для зрителя `handleItem`/`handleLemma` дополнительно ограничены `rate_limits` (строже для `/api/lemma`).
- Атрибуция словаря: ответ содержит `attribution` для значений `source='krdict'` (П-75).
- Открытие шторки шлёт `tap` для каждого `itemId` сегмента (П-19, П-21).

## Доступ и безопасность

**Роли.** `resolveRole(req)` возвращает `owner | viewer | denied`:
- `owner` — валидная подписанная cookie-сессия (HMAC на `SESSION_SECRET`, `HttpOnly`, `Secure`, `SameSite=Lax`, 30 дней). Пароль нигде не передаётся в URL и не лежит в cookie.
- `viewer` — любой другой запрос, если `PUBLIC_FEED=on`; при `PUBLIC_FEED=off` — `denied` (только страница входа) (П-76).
- Права по путям: `/api/chat`, `/api/events`, `/api/checks/answer` (запись), `/api/progress`, `/progress` — только `owner`; для `viewer` отдельные read-only обработчики ленты, проверок и значений (П-69–П-73). Проверка роли выполняется в `route.ts` до любой логики, а не в UI.
- Middleware (`src/middleware.ts`) только ставит заголовки и перенаправляет `/progress` → `/login`; решение о доступе принимают `route.ts` через `resolveRole`, чтобы не зависеть от ограничений Edge-рантайма (нет `timingSafeEqual`). Если возможен Node-рантайм middleware, проверку сессии можно перенести туда.

**Вход владельца (П-54).** `POST /api/login`: пароль сверяется с `OWNER_PASSWORD_HASH` (scrypt/argon2, константное время); лимит 5 попыток за 15 минут на IP (`login_attempts`), одинаковый ответ на любую ошибку; успех выдаёт сессию. Смена пароля = новый хэш и новый `SESSION_SECRET`, все старые сессии сразу недействительны. `POST /api/logout` стирает cookie.

**Защита запросов.**
- Все изменяющие запросы (`POST`) проверяют `Origin`/`Host` (защита от CSRF поверх `SameSite=Lax`) и валидируют тело Zod-схемами; размеры тел ограничены.
- Лимиты запросов (`rate_limits`, ключ — хэш IP + путь): публичная лента — мягкий, `/api/lemma` — строгий, чат (владелец) — N/мин и M/сутки (П-74). Дополнительно можно включить правило Vercel Firewall, если Hobby его поддерживает (проверить по документации при деплое).
- Заголовки: `Content-Security-Policy`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex, nofollow`; `robots.txt` запрещает всё (П-77).
- Приложение без `Secure`-cookie по HTTP не работает; HTTPS даёт Vercel. Токены в URL не используются нигде.

**Секреты и окружения.**
- Production (Vercel): `DATABASE_URL` (пулер, роль приложения), `OPENROUTER_API_KEY` (отдельный, с месячным лимитом на стороне OpenRouter), `OWNER_PASSWORD_HASH`, `SESSION_SECRET`, `ANALYZER_URL`, `ANALYZER_SECRET`, `APP_TZ=Asia/Jayapura`, `PUBLIC_FEED=on`, `EXAM_DATE` (по желанию), модели `MODEL_*`.
- Preview-деплои: либо выключены, либо получают только значения от dev-проекта Supabase; прод-секретов у Preview нет; включена Deployment Protection.
- `KRDICT_API_KEY` и ключи Supabase для миграций живут только на Mac (`.env.local`), в Vercel не попадают.
- Секреты нигде не логируются (логгер без тела запросов и без заголовков авторизации).
- Репозиторий приложения (`korean-threads-app/`, приватный GitHub) не содержит `books/`, `data/`, `.env*`, `backups/`, `*.db`; `books/` и OCR-кэш лежат вне папки репозитория. Перед первым пушем прогоняется `gitleaks`.
- Хостинг: Vercel Hobby рассчитан на некоммерческое использование; приложение личное, это допустимо.
- Лицензия анализатора GPL-2.0: он отдельный процесс (контейнер), не линкуется; доступ только с секретом.

**Лимиты бесплатных планов.** На Vercel Hobby и Supabase Free доплат за превышение нет: при перегрузке сервис остановится, а не выставит счёт. Это защищает бюджет, но не доступность; отсюда кэш и лимиты (П-74). Free-проект Supabase засыпает после недели без активности; при ежедневном использовании это не проявляется.

**Бэкапы.** Ежедневный `pg_dump` на Mac (launchd, 14 копий в `~/backups/`), скрипт восстановления `restore.sh`. Подтверждение восстановимости делается один раз перед боевой раскаткой (Task 21).

## Обработка ошибок

| Ситуация | Поведение | П |
|---|---|---|
| Анализатор недоступен/500 | генерация банка останавливается с сообщением; чат → 502; лента работает | 44, 64 |
| Анализатор 404 на пустой результат | трактуется как `[]` и разбирается как «нет морфем» | 10 |
| OpenRouter недоступен в чате | 502, ничего не сохранено | 44 |
| Параллельный чат владельца | 409 «подожди ответа», второй запрос ИИ не вызывает | 45 |
| Превышен лимит запросов | 429 с коротким русским сообщением, без вызова ИИ | 74 |
| Сессия истекла / неверный пароль | 401 / одинаковый ответ на любую ошибку входа | 54 |
| Запрос зрителя к закрытому пути | 403 без деталей | 71 |
| БД недоступна | короткая страница «сервис временно недоступен», без стека | 56, 67 |
| Значение слова не найдено | шторка показывает слово и «значение не найдено» | 65 |
| Невалидный JSON от ИИ | повтор без `json_schema` → повтор с текстом ошибок → `LlmError` | 44 |
| 429/5xx OpenRouter | два повтора с паузой, затем `LlmError` | 44 |

Все `route.ts` оборачиваются в общий обработчик, который отдаёт короткое русское сообщение и не пропускает стек и внутренние имена (П-67).

## Пробелы плана, которые нужно закрыть при реализации

## Риски

- **Публичный доступ (П-68).** Ссылка открыта всем: возможны боты и перебор паролей, нагрузка на БД и функции. Смягчение: роли и жёсткие права на сервере, лимиты, кэш ленты зрителя, переключатель `PUBLIC_FEED`, зритель не вызывает ИИ (бюджет OpenRouter изолирован), отдельный прод-ключ с месячным лимитом.
- **Авторские права.** В публичную ленту не попадают настоящие вопросы TOPIK (`exam`) и чат-ветки; зрителю показываются банк (написан ИИ), атрибуция словаря и русские пояснения (переформулированы ИИ). Книги и экзамены в облаке только как закрытые текстовые фрагменты для чата. Остаточный риск: пояснения построены на платных учебниках; допущен владельцем.
- **RLS и публичный REST Supabase.** Без RLS публичный anon-ключ раскрывает таблицы. Смягчение: RLS на всех таблицах без политик, приложение только на сервере через роль с минимальными правами, `supabase-js` в клиентском коде не используется; тест миграции проверяет, что у `anon`/`authenticated` нет прав и политик.
- **Потеря состояния памяти.** Free-план без бэкапов с восстановлением. Смягчение: ежедневный `pg_dump` на Mac (14 копий), проверка восстановления до раскатки.
- **Серверлесс-ограничения.** Нет общей памяти и постоянных соединений: пулер на 6543 без prepared statements, дедупликация по журналу, блокировки в БД, `maxDuration` у функции чата, `APP_TZ` задаётся явно (Vercel работает в UTC).
- **Анализатор как отдельный сервис.** Доп. точка отказа для чата (не для ленты). Смягчение: секрет, таймаут, ответ 502 по П-44, лента зрителя и владельца не зависят от него.
- **Качество русских значений и пояснений.** Источник значений — словарь; пояснения грамматики пишет ИИ. Смягчение: выборка из 20 на ручную проверку, бейдж «ИИ» в UI (П-20).
- **OCR экзаменов.** Листы вопросов, вероятно, сканы, ответы на них нужно сопоставить с таблицами. Смягчение: `--dry-run` со стоимостью, пробные 3 страницы, обкатка на одном выпуске (83회), пропуск выпусков без таблицы ответов (Task 6, 11).
- **Совпадение конструкций с анализатором.** Многоморфемные формы («-(으)ㄹ 수 있다») могут не находиться. Смягчение: `grammarMatches` с тестами на реальных фикстурах (Task 5); цель поста, не найденная анализатором, делает пост невалидным (отбраковывается).
- **Сборка анализатора на Python 3.14.** Закреплённые зависимости могут не собраться. Смягчение: `scripts/analyzer.sh` ищет 3.12/3.13 и подсказывает `brew install python@3.12`; при неудаче работа останавливается.
- **Расходы на ИИ.** Банк для 1–4급 — тысячи вызовов. Смягчение: `--dry-run`, пакетная генерация, печать суммы токенов, возобновляемость, выбор моделей по сравнению на образцах.
- **Вопросы «в стиле TOPIK» с ошибочным ключом.** Смягчение: независимое решение другой моделью и проверка, что цель в правильном варианте; метка «в стиле TOPIK» (П-31).
- **Срок.** Три месяца до экзамена. Лента должна запуститься на неполном банке (П-16); вкладка «Тренировка» и аудио отложены.

## Порядок работ и ранний запуск

Лента должна дать пользу как можно раньше, поэтому порядок такой:

1. **Основа**: Task 1–3 (каркас, списки, память).
2. **Материал**: Task 4–5 (клиент, анализатор), Task 6–8 (знания, значения, грамматика), Task 9–10 (посты, банк). Банк генерируется порциями, не ждёт конца.
3. **Лента**: Task 13–15 (выбор, API, UI). С этого момента приложение пригодно, даже при неполном банке.
4. **Проверки**: Task 11–12 (настоящие и «в стиле TOPIK») встраиваются в готовую ленту.
5. **Доступ и деплой**: Task 16 (PWA и README) и новые Task 17–21 (17 — Postgres-слой и RLS; 18 — роли, вход владельца, заголовки, анализатор в контейнере; 19 — режим зрителя; 20 — лимиты; 21 — раскатка, бэкапы, приёмка). Порядок раскатки: Supabase dev/prod с миграциями и RLS → данные (dev, затем prod) → контейнер анализатора → Vercel Production (`icn1`, переменные, `maxDuration`) → ручная приёмка и проверка ролей.

Постоянный `pg_dump`, правило отзыва публичного доступа (`PUBLIC_FEED=off`) и ротация пароля — часть Task 21.

Блокеры владельца, которые нужно снять заранее: `OPENROUTER_API_KEY` (отдельный для прода, с месячным лимитом), `KRDICT_API_KEY`, пароль владельца (для хэша), аккаунты Supabase, Vercel, GitHub, Fly.io, выбор моделей по результатам `bake-off`, согласие на стоимость OCR и полной генерации банка.
