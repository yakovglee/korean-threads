# Решения

Архитектура и деплой: specs/korean-threads/TECH.md. Здесь только то, чего там нет.

- Всё в одном репозитории: код, спеки, PRODUCT.md, DESIGN.md, .impeccable/ и конфиг Claude. Claude Code открывается в этой папке. Книги и OCR лежат вне репозитория, в ../books/.
- Next.js 16, App Router, чистый CSS без Tailwind, иконки lucide-react.
- Источник дизайн-токенов DESIGN.md, src/app/globals.css их повторяет.
- В демо роль задаёт маршрут: / владелец, /viewer зритель.
- Работаем по схеме «Мозг и руки»: Opus 5.5 планирует и принимает, builder и reviewer на Haiku.
- Все субагенты по умолчанию на Haiku (CLAUDE_CODE_SUBAGENT_MODEL в .claude/settings.json). Исключение /impeccable: правки делает основная сессия на Opus, его субагенты запускаются с model: "opus".
- CLAUDE_CODE_SUBAGENT_MODEL_FORCE не включаем: он переведёт на Haiku и субагентов impeccable, несмотря на явный model.
- Тема (П-58, изменено 15.11.2026): по умолчанию системная, кнопка в шапке переключает светлую и тёмную. Тема живёт в атрибуте data-theme на <html>. Выбор хранится в localStorage «theme» и стирается, когда совпадает с системной темой. До отрисовки его применяет инлайн-скрипт в layout.tsx.
- Пока открыта шторка слова, лента заблокирована: WordSheet ставит html[data-sheet="open"], CSS даёт overflow: hidden. Приём с position: fixed на body не берём: страница перестаёт быть прокручиваемой, и подкрутка слова над шторкой (window.scrollBy) не сработает.
- Тесты на Vitest 5. Ему нужны типы Node 22+, поэтому @types/node поднят с ^20 до ^22 (в системе Node 22). БД в тестах: PGlite в памяти с расширениями vector (отдельный пакет @electric-sql/pglite-pgvector) и pg_trgm.
- Драйвер Postgres: postgres.js с prepare: false (пулер Supavisor, transaction mode). bigint читается как number: время в мс и счётчики умещаются в 2^53.
- Слой БД: интерфейс Db (query, tx, close) в src/lib/db.ts. В params только примитивы, JSON передаётся строкой с приведением ::text::jsonb (просто ::jsonb postgres.js кодирует дважды). Вложенные tx запрещены.
- База из DATABASE_URL в .env считается dev-проектом Supabase (решение владельца, 15.11.2026); для прода будет отдельный проект. Переменные лежат в .env, скрипты читают .env.local и .env.
- Папка книг берётся из KB_SOURCE_DIR, а если переменная не задана, то ../books от корня проекта.
- Миграции лежат в supabase/migrations/*.sql. Таблицы учёта нет: каждая миграция идемпотентна (IF NOT EXISTS). Пересмотреть в Task 17.
- kb_chunks.vec имеет тип vector(1024) под baai/bge-m3. Смена модели эмбеддингов потребует миграции.
- loadConfig не бросает исключений: обязательность DATABASE_URL проверяет openDb. Пустая строка в переменной считается «не задано». Параметр имеет тип Record<string, string | undefined>, а не NodeJS.ProcessEnv: типы Next делают NODE_ENV обязательным, и loadConfig({}) не проходит tsc.
- PUBLIC_FEED: лента открыта, только если переменная не задана или равна on, true, 1, yes. Любое другое значение, включая опечатку, закрывает ленту.
- Составные записи списков (15.11.2026). Слово с несколькими омонимами в одной ячейке («계속02/계속01»): headword общая основа, homograph номер первого варианта, pos через «/», исходные варианты в related. Грамматика: «-다가1(1)» даёт headword «-다가» и homograph 1 (номер значения в скобках отбрасывается, записи различаются id и уровнем); скобки в конце убираются из headword, вариант уходит в начало related: если в скобках два слога и больше и ими заканчивается основа («에서부터(서부터)»), это сокращённая форма, она записывается как есть («서부터»); иначе это необязательное продолжение («-기에 앞서(서)»), записывается полная форма («-기에 앞서서»). Правило про два слога — эвристика под текущие данные. В headword после загрузки только хангыль (слоги и отдельные буквы), пробел и дефис: это проверяет тест на реальных файлах.
- Модель забывания (Task 3, 15.11.2026), чего нет в плане. Каждое событие, изменившее состояние, ставит lastEventAt = now; просмотр нового слова состояние не меняет. retrievability: новое слово 0, стабильность 0 даёт 0, нет lastEventAt даёт 1, отрицательный интервал считается нулём. applyEvent возвращает новый объект и вход не меняет.
- getState(db, itemId) без параметра now (в плане он есть, но не нужен): для слова без строки возвращает состояние нового слова и в базу не пишет, строку создаёт saveState. В следующих задачах плана вызовы getState писать с двумя аргументами.
- seedItemState не затирает существующие строки (on conflict do nothing) и вызывается из scripts/ingest-lists.ts после загрузки списков. Словам 1–3급 он ставит last_event_at на момент посева: забывание для них отсчитывается с этого дня.
- getState и saveState уровень слова не проверяют. Правило «память только для 1–4급» (TECH.md, П-8, П-47) обязан держать код событий в Task 14: касание слова 5–6급 в item_state не сохраняется. Внешнего ключа item_state → items нет, поэтому saveState с чужим id создаст лишнюю строку.
- Клиент OpenRouter (Task 4, 15.11.2026), уточнения к плану: openRouterClient(cfg, fetchImpl?, opts?) с опциями retryDelayMs (1000 мс, пауза растёт линейно) и timeoutMs (120 с на один запрос; с повторами и запасным путём json_object один вызов json делает до 6 запросов); сетевая ошибка и тайм-аут не повторяются; temperature уходит в запрос только при явном значении, maxTokens по умолчанию 4000; ответ с finish_reason «length» считается ошибкой, а не результатом; json возвращает только объект и схему сам не проверяет (это делает вызывающий код); полный ключ вырезается из текстов ошибок; заголовки HTTP-Referer и X-Title не отправляются, чтобы не раскрывать проект.
- checkModels ищет модель эмбеддингов в отдельном списке OpenRouter (/embeddings/models, нужен ключ), остальные в /models.
- Анализатор (Task 5, 15.11.2026): сервис удалённый (ANALYZER_URL), поэтому локальный запуск из плана (scripts/analyzer.sh, services/) отложен, пока не понадобится. Клиент уже отправляет заголовок X-Analyzer-Secret и держит тайм-аут 30 с (в плане это Task 18).
- Разметка текста, отличия от плана под настоящие данные. toMorphs берёт части только у слитных токенов (pos с «+»); у токена с одной частью лемма строится из самого токена, а часть идёт вторым вариантом (alt), выбирает список: подходящая часть речи, затем меньший уровень. Формы конструкции = headword и варианты из related до первой пометки «<…>» (после неё синонимы и антонимы); записи вида -(으)ㄹ и -아/어 из примеров плана в списке нет. При сравнении конечное «요» отбрасывается, гласная джамо в начале леммы (ㅏ요, ㅔ요) заменяется слогом. Класс конструкции должен быть совместим с тегом морфемы, EF и EC взаимно допустимы. Существительное + 하다 сначала ищется как слитное слово. resolveMorphs работает по словарю в памяти (loadLexicon, кэш на объект db).
- В itemIds сегмента попадают только однословные конструкции (частицы, окончания). Многословные (115 из 336, например -을 수 있다) находит grammarMatches по всей фразе. Как показывать их по касанию, решить в Task 9 вместе с buildPost.
- Анализатор, ещё отличия от плана: resolveMorphs асинхронный (при первом вызове читает словарь из базы); к существительным относится и 의존명사; unlisted считается по вхождениям, без удаления повторов (учесть при расчёте доли в Task 9); 404 считается пустым результатом, только если это ответ самого сервиса, а «Not Found» несуществующего маршрута — ошибка; секрет уходит только по https (кроме localhost), редиректы запрещены.
