- Миграции лежат в supabase/migrations/*.sql. Таблицы учёта нет: каждая миграция идемпотентна (IF NOT EXISTS). Пересмотреть в Task 17.

- Составные записи списков (15.11.2026). Слово с несколькими омонимами в одной ячейке («계속02/계속01»): headword общая основа, homograph номер первого варианта, pos через «/», исходные варианты в related. Грамматика: «-다가1(1)» даёт headword «-다가» и homograph 1 (номер значения в скобках отбрасывается, записи различаются id и уровнем); скобки в конце убираются из headword, вариант уходит в начало related: если в скобках два слога и больше и ими заканчивается основа («에서부터(서부터)»), это сокращённая форма, она записывается как есть («서부터»); иначе это необязательное продолжение («-기에 앞서(서)»), записывается полная форма («-기에 앞서서»). Правило про два слога — эвристика под текущие данные. В headword после загрузки только хангыль (слоги и отдельные буквы), пробел и дефис: это проверяет тест на реальных файлах.

Порядок кандидатов: сколько разных слов запроса найдено, затем число вхождений, затем id. Если эмбеддинг запроса не получился, поиск идёт только по тексту. Уже загруженный файл пропускается без чтения страниц; изменённый файл с тем же путём заменяет старые чанки в одной транзакции; тот же файл под вторым именем пропускается. Чанк не смешивает страницы, у .md страница null; ref — ближайший заголовок «#», иначе «стр. N».

Файл экзамена с именем в битой кодировке не пропускается (в плане было «пропускать»): содержимое у него обычное. --dry-run бесплатный: читает только файлы, модель и базу не трогает; оценку токенов печатает по data/ocr/usage.json, когда там есть замеры (в плане оценка по трём пробным страницам шла внутри --dry-run). Флаги сверх плана: --only, --exclude, --force-ocr (все страницы документа распознаёт модель, текстовый слой не берётся), --ocr-page (пробное распознавание страницы с печатью текста, база не трогается), --no-embed, --jobs. Без --yes скрипт ничего не отправляет в модель: ни страниц на распознавание, ни текста на эмбеддинги.

- Значения слов (Task 7), ещё отличия от плана. ingestGlosses принимает llm и onProgress и возвращает { done, missing, chosenByAi, skipped }: done — значение из словаря, missing — словарь ответил, но подходящего значения нет (строка item_notes с gloss_ru null, её потом заполняет ИИ), skipped — слово осталось без строки (сеть, ошибка модели, нет модели) и будет спрошено в следующий запуск. pickEntry берёт запись, только если по части речи подходит ровно одна; во всех остальных случаях (несколько записей или единственная с другой частью речи) решает модель по подсказке и может ответить «ни одна». Пять слов подряд без ответа словаря или модели прерывают прогон. В gloss_ru идут до трёх разных переводов значений записи через « · », в explanation_ru — русское толкование первого значения.

- Посты (Task 9, 16.11.2026), отличия от плана. Все функции src/lib/posts.ts асинхронные (база — Db). buildPost возвращает ещё grammarIds: конструкции, совпавшие где-либо в абзаце по grammarMatches. Цель-конструкция засчитывается по itemIds или grammarIds: в сегмент попадает одна лучшая конструкция на морфему (для 고 это -고 연결어미), а целью может быть другая с той же формой. saveThread(db, thread, opts) без отдельного списка itemIds: post_items берутся из сегментов каждого поста. Доля слов вне списков считается по вхождениям: unlisted / (unlisted + слова из списков).
- Правило уровня в validatePost (режим bank) смотрит только на itemIds, то есть на то, что размечено в сегментах: там на морфему выбрана одна конструкция, при равной форме с меньшим уровнем. grammarIds в правиле уровня не участвуют: в них попадают все конструкции с подходящей формой, включая одноимённые 5–6급 («-네» 2급 и «-네1» 6급), и по ним отсеивался бы почти любой пост. grammarIds нужны только чтобы засчитать цель. Ошибка анализатора в buildPost и buildCheck — исключение, а не { ok: false }: это сбой сервиса, а не негодный текст.
- Генерация банка (Task 10, 16.11.2026), отличия от плана. Разметка принимает список предпочитаемых id (opts.prefer у analyzeFull, buildPost, buildCheck): среди омонимов слова и конструкций с одной формой берётся цель поста. - Общие статьи омонимов (Task 7, 16.11.2026). После загрузки значений `scripts/ingest-glosses.ts --fix-shared` ищет омонимы одного слова, которым записана одна и та же статья словаря, и заново распределяет статьи одним вызовом модели роли write по всем омонимам группы сразу (правило: разным омонимам разные статьи). Выбор по одному омониму дешёвой моделью дал такие пары у 10 слов из 217 с омонимами. Порядок загрузки значений в новую базу: без флагов (словарь), затем --fix-shared, затем --ai (слова без статьи).
- Лента (Task 13, 16.11.2026), отличия от плана и решения. Все функции асинхронные (Db). Приоритеты слов считаются в коде, суммы по веткам — одним SQL-запросом (приоритеты уходят JSON-параметром). Новые слова ветки — is_new и ещё не введённые (introduced_day пуст); слово считается в порции один раз. Добор в три шага: (1) взвешенная выборка из топ-3n свежих веток с лимитом новых; (2) показанные раньше всех, с лимитом; (3) оставшиеся без лимита, сначала с наименьшим числом новых. Шаг 3 ставит «лента не пустеет» (П-11, П-15, TECH.md) выше лимита 6 новых слов (П-14): в тонком банке лимит может быть превышен. Шаг 2 может выдать недавно показанную ветку, когда непоказанная не проходит лимит (П-13 уступает П-14). Слот подтяжки берётся из всех свежих веток со stretch_item_id. Проверок в порции floor(n / 12) плюс одна с вероятностью остатка: при порциях меньше 12 веток проверка приходит в среднем раз в 12 веток.
